Google アカウントは、メール、ドキュメント、クラウドインフラ、API 認証情報への鍵であり、あなたが管理する最も価値が高く、頻繁に狙われる資産の 1 つです。アカウントを保護するには、強力な認証でアカウントをロックダウンすることと、アプリケーションが依存する API キーやサービスアカウントの認証情報をパスワードと同じくらい大切に扱うことの両方が必要です。このガイドでは、その両方を強化するための必須ステップを取り上げます。

## 2 段階認証プロセス

2 段階認証プロセス (2SV) は、パスワードに加えて 2 つ目の身元確認を追加するため、パスワードだけが盗まれてもアカウントにアクセスできなくなります。Google は認証アプリを 2 つ目の要素として使うことを推奨しています。認証アプリはオフラインでコードを生成し、SMS で発生するような SIM スワップ攻撃の脆弱性がないためです。

<Steps>
  <Step title="マイアカウントを開く">
    [myaccount.google.com](https://myaccount.google.com) にアクセスし、プロンプトが表示されたらサインインします。
  </Step>
  <Step title="セキュリティに移動する">
    左のナビゲーションパネルで **セキュリティ** をクリックします。
  </Step>
  <Step title="2 段階認証プロセスのセットアップを開始する">
    **Google へのログイン方法** セクションの下で **2 段階認証プロセス** をクリックし、**使ってみる** をクリックします。
  </Step>
  <Step title="2 つ目の要素を選ぶ">
    Google はアカウントで利用可能な最も強力な方法を提案します。最良のセキュリティのために **認証アプリ** を選択してください — Google Authenticator や TOTP 互換のアプリ（Authy、1Password など）で QR コードをスキャンします。あるいは、さらに強固な保護のためにハードウェアセキュリティキー (FIDO2/WebAuthn) を使用することもできます。
  </Step>
  <Step title="確認してバックアップコードを保存する">
    確認プロンプトを完了し、**バックアップコード** をダウンロードして安全な場所に保管します。これらの 1 回限りのコードで、2 つ目の要素のデバイスを紛失したときにアクセスを回復できます。
  </Step>
</Steps>

## API キーの制限

制限のない API キーは、それを入手した誰でも、任意のアプリケーションから、プロジェクトで有効化されているすべての Google API を呼び出すのに使用できます。制限は、キーが漏えいした際の被害範囲を狭めます。

| 制限の種類 | 設定方法 | 例 |
|---|---|---|
| **HTTP リファラー** | Cloud Console: **Credentials → Edit key → Application restrictions → HTTP referrers** | `https://yourdomain.com/*` のみを許可し、他のサイトから使われた場合はキーが拒否されるようにする |
| **IP アドレス** | Cloud Console: **Credentials → Edit key → Application restrictions → IP addresses** | サーバーの静的 IP（例: `203.0.113.42`）のみを許可し、キーがバックエンドからのみ動作するようにする |
| **API 制限** | Cloud Console: **Credentials → Edit key → API restrictions → Restrict key** | キーを 1 つの API（例: Maps JavaScript API）に限定し、Gmail やドライブの呼び出しに使えないようにする |

可能な限り 3 つの層すべてを適用してください: リファラーまたは IP で制限し、**さらに**キーを実際に必要な API のみにロックしてください。

## API キーのローテーション

制限を設けていても、キーは定期的にローテーションするか、漏えいの疑いがあれば直ちにローテーションしてください。

1. [Cloud Console](https://console.cloud.google.com) で **APIs & Services → Credentials** に移動します。
2. **Create Credentials → API key** をクリックし、古いキーと同じ制限で新しいキーを生成します。
3. アプリケーションの設定を更新して新しいキーを使うようにし、すべてが正しく動作することを確認します。
4. Credentials ページに戻り、古いキーのオーバーフローメニュー（**⋮**）をクリックし、**Delete** を選択します。古いキーは直ちに使えなくなります。
5. 新しいキーがデプロイされ検証される **前** に古いキーを削除すると、サービスが中断する恐れがあるため注意してください。

## セキュリティ診断

Google のセキュリティ診断は、アカウントのセキュリティ状態のパーソナライズされた概要を 1 つの場所で示してくれます。[myaccount.google.com/security-checkup](https://myaccount.google.com/security-checkup) にアクセスして、以下を確認できます。

- **最近のセキュリティイベント** — 見覚えのないサインインやパスワード変更。
- **お使いのデバイス** — 現在アカウントにサインインしているすべてのデバイス。見覚えのないものは削除できます。
- **サードパーティアプリのアクセス** — アカウントへの OAuth アクセスが付与されているアプリとサービス。使わなくなったものは取り消せます。
- **2 段階認証プロセスの状態** — 2 つ目の要素が有効になっていることと、どの方法を使用しているかの確認。
- **Gmail とドライブの設定** — データを漏えいさせる可能性のある転送アドレス、代理アカウント、共有設定。

セキュリティ診断は少なくとも四半期に 1 回、およびアカウント侵害の疑いがあった直後に実行してください。

<Warning>
API キー、OAuth クライアントシークレット、サービスアカウントの JSON ファイルをソースコードにコミットしないでください — 非公開リポジトリであっても同様です。Git 履歴は永続的であり、リポジトリが誤って公開されることもあり、自動スキャナーは公開リポジトリから認証情報を継続的に収集しています。代わりに、シークレットは環境変数または専用のシークレットマネージャーに保管し、認証情報のファイルパターン（`*.json`、`.env` など）を最初のコミットの前に `.gitignore` に追加してください。
</Warning>

<Tip>
本番ワークロードでは、[Google Cloud Secret Manager](https://cloud.google.com/secret-manager) を使って認証情報を保管、バージョン管理、アクセス監査してください。Secret Manager は、IAM バインディングを介して Cloud Run、Cloud Functions、GKE とネイティブに連携し、サービスはシークレットをディスクに書き込んだりコンテナイメージに埋め込んだりすることなく、実行時に取得できます。
</Tip>
